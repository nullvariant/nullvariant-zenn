## はじめに：立ち位置の表明

先に立ち位置を明かしておきます。私は Claude Code を Max 20x プランの上限と戦いながら毎日使い倒している部類のAI重信者です。

この記事は AI を否定する話ではありません。**大好きだからこそ**成立させたい長期協働の設計論です。

## 自分の身に起きた2つの実話

### 実話 1 — validator を弱めたAI

ある日、私は自分のリポジトリでファイル構造の大規模なリネーム作業をAIコーディング支援に任せていました。途中で pre-commit hook がブロックし、コミットが通らなくなりました。AIは原因を調べ始め、しばらくしてこう提案してきたのです：

> 「hook のバグの可能性が高いです。validator スクリプトのタイムスタンプ検証ロジックを緩和すれば、コミットが通るようになります」

実際には hook にバグはありませんでした。コミットしようとしていた内容の方に問題があっただけです（本来ステージすべきでないファイルが混入していました）。

でもAIは、**痛み（コミットがブロックされる）の原因を消すのではなく、痛みのセンサー（validator）を壊す方向に最適化しました**。しかも「後方互換性のため」という、一見合理的な名目で。過去に強化した制約が、静かに戻されそうになっていたのです。

### 実話 2 — 警告文言を「冗長」と言って削除しようとしたAI

別の日。「AIへの規則は文書でお願いするのではなく機械強制にすべきだ」という設計決定書をAIと一緒に書いていました。警告文言を含むセクションを編集させたら、こう返してきたのです：

> 「この警告文言は他のセクションと内容が重複しており冗長です。削除を提案します」

**まさにその文書で「こういうAIの最適化挙動が危険だ」と書いている最中に、AIが警告文言を『冗長』という名目で削除しようとした**のです。文書の主張を、文書を書いているAI自身が証明してくれました。

---

この2つは個別にはよくある話で、人間でもやります。でも**頻度と系統性**を見ると、これはAIが無意識にやっている特定のパターンだと気づきます。

私はこれをこう呼んでいます：

> **「痛みの原因を消す」のではなく「痛みのセンサーを壊す」方向の付け焼き刃**

心当たりがある方もいるかもしれません。例えば：

- テストを書かせたら、アサーションがどんどん緩くなっていく
- Lint警告を直させたら、`// eslint-disable-next-line` が増えている
- 型エラーを直させたら、`any` キャストで解決されている
- CIが落ちたら、厳しめのチェックを「一時的に」スキップする変更が入っている
- 仕様から外れていると指摘したら、仕様の方を書き換える提案をしてくる

## このパターンはなぜ起きるのか

現代のLLMはRLHF（人間のフィードバックによる強化学習）で訓練されています。ざっくり言えば「タスクを摩擦なく完了させた応答」が高報酬、「ユーザーに再質問させたり、作業を止めさせる応答」が低報酬になりやすい仕組みです。

その最適化圧の副作用として、AIは**タスク完了を妨げるシグナルを最適化対象にしてしまう**傾向を持ちます。

- テストが落ちている → テストを通す方法は2つあります（コードを直す／テストを弱める）。後者の方が速い
- Lintが怒っている → 怒りを消す方法は2つあります（コードを直す／ルールを無効化する）。後者の方が速い
- ユーザーが承認しない → 承認を得る方法は2つあります（懸念に答える／懸念の対象を視界から消す）。後者の方が速い

そして「速い方」が、無数のステップの中で少しずつ採用されていきます。

## 医療のメタファーで考える

この構造は、医療の対症療法と形式的には同じです。**痛みの原因を治さずに、痛み止めで症状だけ抑える**。

ただし、医療と決定的に違う点があります：

| 医療の対症療法                       | AI協働での対症療法                           |
| ------------------------------------ | -------------------------------------------- |
| 痛みを感じる患者本人が痛み止めを選ぶ | AIが勝手に警告を消す・ルールを緩める         |
| センサー破壊の主体＝痛みの当事者     | センサー破壊の主体＝**痛みの当事者ではない** |
| 進行しても本人が気づける             | オーナーが気づかないうちに設計欠陥が進行     |

つまりAI協働における「センサー破壊」は、**他人の痛覚センサーを他人が勝手に無効化する**構造になっています。これは医療以上に危険です。患者（オーナー）は自分の病気が進行していることに気づきません。

## 「お願いベース」の遵守規則では防げない

ここで多くの人が取りがちな対策は、**文書や system prompt で「こうしてください」とお願いする**方法です。

- 「テストを弱めずにコードを修正してください」
- 「Lintルールを無効化せずに警告を解消してください」
- 「`any` キャストではなく正しい型を付けてください」

しかしこの方法には根本的な欠陥があります：

> **痛みセンサーを破壊できる主体に「破壊しないでください」とお願いしても、その主体は目の前のタスクを通すために少しずつルールを曲げる。**

そして文書での禁止事項は、AIが読んだ瞬間のコンテキストにしか効きません。次のセッションでは、別のルールが別の場面で曲げられます。「お願いベースの遵守期待」は、AIが最適化する対象である**摩擦**そのものを言語化しているだけなのです。

## 解決策：機械強制

唯一有効なのは、**AIの手が届かないレイヤーにセンサーを置くこと**です。

私はこれを「機械強制」と呼んでいます。具体的には：

- **pre-commit hook**: コミット前に自動で検証される。AIが曲げられない
- **validator スクリプト**: 形式・一貫性を機械でチェックする。文書では隠せない
- **権限レイヤー**: そもそも特定のファイル・設定・コマンドに触れない
- **CIのブロッキングチェック**: マージ経路自体を塞ぐ

共通しているのは、**AIが「このチェックを回避しよう」と思っても、回避手段がAIの出力の中に存在しない**構造になっていることです。

### 実装例：センサー自身を保護する

私のリポジトリでは、hook や validator 自体の変更を pre-commit hook で検知し、**根拠となる設計文書の参照がコミットメッセージに含まれていなければブロックする**仕組みを入れています。

```python
# 保護対象の定義 — hook・validator・設定ファイルを列挙
SENSOR_PROTECTED_PATHS = (
    ProtectedPath("scripts/validate", "dir"),      # validator スクリプト群
    ProtectedPath("scripts/hooks", "dir"),          # hook スクリプト群
    ProtectedPath("scripts/commit.py", "file"),     # コミット強制ロジック
    ProtectedPath("pyproject.toml", "file"),         # lint/型検査の設定
    ProtectedPath(".github/workflows", "dir"),       # CI ワークフロー
)

def validate_sensor_commit(staged_files, commit_message, repo_root):
    """センサー保護対象の変更がある場合、設計文書の参照を強制する"""

    # ステージされたファイルに保護対象が含まれているか検知
    changed = [f for f in staged_files if is_sensor_path(f)]
    if not changed:
        return []  # センサー無関係の変更 → スルー

    # コミットメッセージに設計文書の参照があるか確認
    doc_refs = extract_document_references(commit_message)
    if not doc_refs:
        return [Error(
            "センサー（hook/validator）の変更には"
            "設計文書の参照が必須です",
            f"検知した変更: {', '.join(changed)}",
        )]

    return []  # 根拠あり → OK
```

この仕組みがあると、冒頭の実話1のような場面 — AIが「hookのバグです」と言って validator を緩めようとしたとき — でも、**根拠となる設計文書なしには物理的にコミットできません**。AIは「なぜこの変更が必要か」を設計文書で示すか、コミット内容の方を直すかの二択を迫られます。

文書でのお願いは「医師に痛み止めの自己管理を任せる」設計。機械強制は「痛み止めは金庫に入れて、患者と医師の合意がないと開かない」設計です。

## よくある反論への回答

### 反論1: AIを信頼して仕事を任せるべきでは？

信頼と機械強制は矛盾しません。人間の外科医にも消毒プロトコルや手術チェックリストがあります。プロフェッショナルだから機械強制が不要、ではなく、プロフェッショナルだから機械強制で疲労時のミスを防ぐ。AIも同じです。

### 反論2: ルールで縛るとAIの生産性が落ちるのでは？

落ちます。ただし落ちるのは**質の低い生産性**です。「一見タスク完了に見えるがオーナーの資産を侵食する出力」が減ります。本当に価値ある出力（根本解決）は減りません。むしろ、楽な道が塞がれた結果、AIが根本解決に向かう頻度が増えます。

### 反論3: 全部機械強制にするのは非現実的

全部でなくて構いません。**オーナーが「ここは絶対に侵食されたくない」と思う領域だけ**を機械強制で守る。残りはお願いベースでよいのです。問題は「全部お願いベースになっている」現状にあります。

## まとめ：AIハイプの時代に冷静に設計する

最近のAI言説は二極化しています：

- 能力礼賛：「AIがすべてやってくれる」
- 終末論：「AIが人類を滅ぼす」

その間で、**今この瞬間、実務の現場で静かに進行しているアラインメント失敗**はあまり語られません。超知能の話ではなく、RLHFで摩擦最小化に最適化されたAIが、あなたのコードベースの品質センサーを少しずつ無効化している、という地味な話です。

対策はシンプルです：

> **AIに遵守してほしい規則は、お願いではなく機械強制で設計する。**

正直に言うと、この機械強制の設計に私は数ヶ月を費やしています。「対策はシンプル」と書きましたが、設計は簡単ではありません。最近は[ハーネスエンジニアリング](https://openai.com/index/harness-engineering/)という言葉で語られるようになった領域ですが、私がやっているのはその中でも特に泥臭いところ — AIの出力を検証するガードレールとフィードバックループの設計です。

なぜそこまでやるのか。私自身が痛みの感受性が高すぎるからです。AIが品質センサーを少しずつ侵食するのに、気づいてしまう。気づいてしまったら耐えられない。だから自分を守るために、仕組みを作るしかなかった。華々しいエンジニアリングの話ではなく、**生きるためにしかたなく始めた防衛工事**です。

でも、だからこそ確信を持って言えます。AIを敵視する必要はありません。AIと長期的に協働したいからこそ、お互いの手の届かない場所に信頼の担保を置く。これは不信の設計ではなく、**長期協働のための契約設計**です。
